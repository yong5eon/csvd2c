# 원문 레코드 조회 요구사항

## 목적과 범위

검증에 실패한 데이터 레코드를 검증 전 필드 값으로 보관할 수 있도록 `CSV.raw() -> Optional[List[str]]`를 추가한다. 원본 출처와 작업 브랜치는 [이슈 README](./README.md)를 따른다.

포함 범위는 원문 조회, 읽기·종료에 따른 원문 상태 관리, 기존 계약의 회귀 검증과 관련 사용 문서다. 구현 중 확인된 표준 writer 제약에 따라 사용자가 승인한 Python 3.10 최소 버전 변경도 포함한다. 이 문서는 요구사항 분석과 명세이며, 구현 완료를 뜻하지 않는다.

### 이슈 원문과 현재 계약의 차이

이슈의 “`header()`로 읽은 레코드”는 현재 코드에서는 헤더 Validator에 의해 `open()`이 소비한 레코드에 해당한다. `header()`가 다시 파일을 읽도록 변경하는 요구로 해석하지 않는다. 헤더 Validator가 없으면 파일 첫 레코드도 일반 데이터이므로 `row()`·`rows()`로 읽을 때 원문 대상이다.

현재 `HeaderError`는 행 오류와 별도 클래스이며 `message`와 `value`를 가진다. 이슈 #13을 이유로 행 번호를 추가하거나 행 오류로 통합하지 않는다.

실행 확인에서도 `raw()` 부재, `Strip` 후 실패한 `ColumnError.value == ''`, 예외로 종료된 동일 generator의 소진, 이후 `row()`의 다음 레코드 반환을 확인했다. 상세 결과는 [분석·검증 기록](./tasks/1793707424103.md)을 따른다.

## 확정 요구사항

### R1. 조회 API와 원문의 의미

- 인자 없는 `CSV.raw()`는 가장 최근 데이터 읽기 시도의 결과를 `Optional[List[str]]`로 반환한다.
- 원문은 설정된 디코딩과 CSV 파싱이 끝난 뒤, 행·컬럼 Validator를 적용하기 전의 필드 목록이다. 파일 바이트나 물리 줄 텍스트가 아니다.
- 원문이 있으면 호출할 때마다 새로운 목록을 반환한다. 반환값 수정과 검증 결과 목록 수정이 내부 원문이나 다음 조회에 영향을 주지 않아야 한다.
- 조회는 파일 위치·offset·limit을 변경하거나 검증기를 실행하지 않는다.
- CSV 파서가 반환한 빈 목록 `[]`도 읽은 레코드다. 이를 “원문 없음”인 `None`으로 취급하지 않는다.

### R2. 데이터 읽기와 상태 전이

| 이벤트 | 이후 `raw()` 결과 |
| --- | --- |
| 생성 직후 또는 파일을 열고 데이터 읽기 전 | `None` |
| 헤더 Validator가 헤더를 읽고 변환·검증 | `None` 유지 |
| `header()` 조회 | 현재 원문 상태 유지 |
| offset 레코드를 건너뜀 | 건너뛴 레코드를 원문으로 노출하지 않음 |
| 범위 안 레코드 파싱 성공, 검증 성공 | 해당 레코드의 검증 전 필드 목록 |
| 범위 안 레코드를 읽은 뒤 `RowError` 또는 `ColumnError` | 실패 레코드의 검증 전 필드 목록 |
| 다음 읽기에서 EOF 또는 limit 도달 | `None` |
| 데이터 읽기 또는 offset 건너뛰기 중 파싱·디코딩 실패 | `None` |
| `close()` 또는 컨텍스트 종료 | `None` |
| 같은 인스턴스를 다시 열고 데이터 읽기 전 | `None` |

- `row()`와 `rows()`는 같은 원문 상태를 사용한다. 섞어 읽으면 마지막으로 실제 읽기를 수행한 레코드가 조회 대상이다.
- 마지막 허용 레코드를 반환한 직후에는 원문을 조회할 수 있다. 다음 읽기 시도가 limit 또는 EOF로 끝날 때 `None`으로 바뀐다.
- `rows()`의 iterator 생성 자체는 레코드 읽기가 아니다. 순회 중 레코드를 읽을 때 갱신한다.
- `list(csv.rows())`처럼 정상 소진한 뒤에는 마지막 종료 확인도 읽기 시도이므로 `None`이다. 각 레코드 원문은 순회 본문에서 조회해야 한다.

### R3. 검증 실패와 계속 처리

- `row()`의 검증 오류를 열린 파일 컨텍스트 안에서 잡으면 `raw()`로 실패 레코드를 얻고 다음 `row()`로 이어갈 수 있어야 한다.
- 앞선 행 Pattern의 제자리 변경·새 목록 반환이나 앞선 컬럼 Pattern의 값 변환에도 원문을 유지한다.
- `rows()`에서 검증 예외가 전파되면 실패 원문을 유지한다. 예외로 종료된 동일 generator를 재개하도록 바꾸지는 않는다.
- 컨텍스트 밖에서 예외를 잡으면 이미 `close()`가 원문을 지운다. 원문 저장 예시는 `with` 안에서 검증 오류를 처리해야 한다.

### R4. 호환성과 제약

- `RowError`, `ColumnError`, `HeaderError`의 생성자·속성·전파 방식과 Pattern·Validator 시그니처를 변경하지 않는다.
- 기존 읽기 위치 공유, 검증 순서, 헤더 매핑, 인자 재정의, 물리 라인 번호, offset·limit 계산과 자원 정리를 유지한다.
- 파싱·디코딩 오류를 검증 오류로 포장하거나 자동 복구·재시도하지 않는다.
- 같은 CSV 설정으로 다시 쓰고 읽었을 때 필드 값은 보존되어야 한다. 따옴표·escape 표기와 파일 바이트의 동일성은 보장하지 않는다.
- `raw()`를 호출하지 않는 기존 사용 방식의 결과와 오류 동작을 유지한다. 원문 보존을 위해 현재 레코드에 비례하는 추가 메모리는 필요하지만 전체 파일이나 과거 레코드 이력은 저장하지 않는다.

### R5. 사용자 문서

- 한국어·영어 상세 매뉴얼에 반환형, 상태 갱신·초기화 규칙, 오류 `value`와의 차이를 설명한다.
- `row()` 반복에서 실패 레코드를 같은 설정의 `csv.writer`로 저장하는 예시를 제공한다.
- 동일 `rows()` generator는 검증 예외 후 종료된다는 점과 계속 처리하려면 `row()` 반복을 사용해야 한다는 점을 명시한다.
- 원문은 파싱된 필드 목록이며 CSV 표기는 바뀔 수 있다는 점과 컨텍스트 종료 후에는 원문을 조회할 수 없다는 점을 명시한다.
- 기존 거부 기록 샘플과 루트 README 요약의 설명이 새 API와 충돌하지 않는지 확인한다. 상세 계약은 매뉴얼에서 관리한다.

### R6. 승인된 최소 Python 버전 변경

- Python 3.9.13의 표준 `csv.writer`가 필드 안 escape 문자를 보존하지 못해 A11 왕복 검증이 실패했다. csvd2c를 사용하지 않는 표준 라이브러리만의 재현에서도 실패하고 Python 3.10.11에서는 정상임을 확인했다.
- 근거는 [CPython 오류 #56387](https://github.com/python/cpython/issues/56387)이며, 사용자는 최소 Python 버전을 3.10으로 변경하도록 승인했다.
- `python_requires`, Trove 분류자, CI, 샘플 구문 기준과 설치 문서를 Python 3.10 이상으로 일치시킨다. Python 3.11~3.14 지원과 `Optional[List[str]]` 반환 계약은 유지한다.
- 표준 writer 버그 우회, 조건부 테스트 생략, Python 문법 일괄 현대화는 추가하지 않는다.

## 최소 해결 방향과 제외 범위

공통 데이터 읽기 경계에서 검증 전 원문 한 건을 보존하고, 조회 시 복사본을 주며, 읽기 실패와 생명주기 종료 때 비우는 방식이 현재 구조에서 가장 직접적이다. 문자열 필드 목록이므로 깊은 복사나 별도 저장 서비스는 필요하지 않다. 이는 설계 제안이며 내부 필드명이나 구현 세부를 API 계약으로 고정하지 않는다.

다음 항목은 추가하지 않는다.

- 오류 객체에 전체 원문 추가, 새로운 오류·Pattern 체계 도입
- 원문 이력, 자동 덤프·수정·재삽입, 실패 generator 복구
- 별도 옵션·콜백·재시도·동시성 제어
- 파일 바이트 복원, 새 dialect 인자, 기존 헤더 API 변경

읽기 전 인자·매핑 오류나 오래된 iterator 호출은 원문의 갱신 기준으로 이슈에 명시되어 있지 않다. 해당 오류의 기존 발생 순서와 파일 미소비 계약은 유지하고, 이 분석에서는 별도의 원문 초기화 정책을 추가하지 않는다. 구현 중 이 경계에 대한 새로운 외부 계약이 필요해지면 임의 확정하지 않고 확인한다.

미확정 사항은 없다. 구현 단계에서는 승인된 R6를 포함한 명세와 작업 계획에 따라 진행한다.
