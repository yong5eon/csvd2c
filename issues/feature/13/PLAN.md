# 원문 레코드 조회 작업 계획

## 기준과 현재 상태

[확정 요구사항](./REQUIREMENTS.md)의 R1~R5와 인수 기준 A1~A12를 구현한다. 저장소·브랜치·병합 대상은 [이슈 README](./README.md)를 따른다.

- 작업 계획 작성 완료, 제품 구현 미착수
- `raw()` 반환형은 `Optional[List[str]]`로 확정
- 관련 기존 테스트 93개 통과는 [이전 분석 기록](./tasks/1793707424103.md)의 기준 결과이며 신규 기능 검증 결과가 아님
- 이번 요청에서는 계획서와 작업 기록만 작성하고 코드·테스트·사용자 매뉴얼은 변경하지 않음

## 구현 방향

[CSV](../../../src/CSV.py) 안에 최근 원문 한 건만 보존한다. 별도 클래스나 옵션 없이 기존 `header()`의 복사본 조회 방식과 공통 `read_record()` 경계를 활용한다.

1. 생성·파일 열기·종료 시 원문 상태를 초기화한다.
2. `read_record()`에서 limit 검사·offset 처리·실제 읽기에 앞서 이전 원문을 비운다. 읽기 실패는 기존 예외 그대로 전파하고, 성공한 데이터 레코드만 복사해 보존한다.
3. 기존 `row()`·`iterate()`는 검증 전 원문이 보존된 레코드로 현재 검증 흐름을 계속 사용한다.
4. `raw()`는 원문이 `None`인지 명시적으로 구분하고, 있으면 얕은 복사본을 반환한다. 빈 목록 `[]`도 유효한 레코드로 유지한다.

예외 처리로 원문을 뒤늦게 복구하거나 검증 뒤 목록을 복사하지 않는다. 성공한 레코드의 원문은 다음 실제 읽기 시도까지 유지하므로 `rows()` iterator 생성이나 헤더 조회에 초기화를 넣지 않는다. 기존 읽기 전 인자·매핑 검사와 오래된 iterator 검사의 순서는 바꾸지 않는다.

## 인수 기준별 검증

| 기준 | 테스트 구성과 확인할 결과 |
| --- | --- |
| A1 | 변환 없는 성공과 행·컬럼 변환 성공에서 검증 전 필드 비교. `raw()`를 여러 번 호출한 뒤 다음 레코드와 limit 소비가 동일한지 확인 |
| A2 | 입력 목록을 제자리에서 바꾸는 행 Pattern과 새 목록을 반환하는 Pattern을 각각 사용. 후속 성공·행 오류 모두에서 최초 필드 보존 |
| A3 | 앞쪽 컬럼을 클린징한 뒤 뒤쪽 컬럼에서 실패. 오류의 `value`는 기존 계약대로 두고 `raw()`는 최초 전체 필드 반환 |
| A4 | 두 번 조회한 목록이 서로 다른 객체인지 확인. 반환 목록의 수정·삭제·추가와 성공 결과 목록 변경 후에도 내부 원문 불변 |
| A5 | 생성·open 직후·close·컨텍스트 정상/예외 종료·재오픈의 `None` 확인. 빈 줄을 파싱한 `[]`와 구분 |
| A6 | 변환된 헤더 자동 소비와 반복 조회, offset 건너뜀, 헤더 미주입 첫 레코드 포함 여부 확인. 데이터 읽기 뒤 `header()` 조회가 원문을 유지하는지도 확인 |
| A7 | 빈 파일·offset 초과·limit=0·마지막 허용 레코드·다음 종료 시도 순서별 원문 상태 확인. limit 도달 시 뒤 레코드를 읽지 않는 기존 동작 유지 |
| A8 | 데이터 읽기와 offset 건너뛰기에서 파싱·디코딩 실패를 각각 유발. 원래 예외와 `None` 확인. 데이터 읽기 실패는 이전 원문이 있는 상태에서도 검증 |
| A9 | 열린 컨텍스트 안의 `row()` 반복에서 행 오류와 컬럼 오류 원문을 저장하고 다음 정상 레코드 처리. 실패도 기존처럼 limit을 소비 |
| A10 | `rows()` 생성만으로 상태가 바뀌지 않음, 순회 본문의 원문, 검증 오류 직후 실패 원문과 동일 generator 종료, 정상 소진 후 `None`, `row()`와 혼합 사용 확인 |
| A11 | 구분자·따옴표·인용 개행·escape 문자가 포함된 합성 CSV를 읽고 같은 설정의 `csv.writer`로 저장한 뒤 재파싱. 바이트가 아닌 필드 목록 동등성 비교 |
| A12 | 기존 읽기·범위·헤더·오류 테스트, 변경된 샘플 실행, 공개 반환 타입과 한국어·영어 문서 일치 확인 |

읽기 모드 `rb`·`r`·`rt`의 공통 경로는 대표 성공·오류 사례를 매개변수화해 확인한다. 문자열 필드 목록의 얕은 복사가 충분한지 실제 변형 테스트로 검증하며, 데이터는 임시 디렉터리에 만든 비민감 합성 CSV만 사용한다.

디코더는 뒤쪽 바이트를 미리 읽을 수 있다. A8의 “이전 원문이 있는 상태”는 먼저 정상 레코드를 얻었음을 확인한 뒤 오류를 유발하는 입력·스트림으로 구성한다. 잘못된 바이트를 단순 연결한 파일이 반드시 두 번째 `row()`에서 실패한다고 가정하지 않는다.

## 검증 실행 방법

저장소 루트에서 프로젝트 패키지가 이 작업 트리의 소스를 사용하는 환경의 `python`으로 실행한다. 아래 모듈 선택 명령에는 `tests`를 모듈 검색 경로로 지정한다.

신규 테스트 작성과 구현 단계:

```shell
python -m unittest discover -s tests -p test_raw.py
```

코드·문서 예시 반영 후 관련 회귀 테스트를 한 번에 실행:

```shell
python -m unittest test_raw test_csv test_range test_header test_error_context test_samples
```

- 샘플 테스트는 별도 프로세스에서 설치된 패키지를 사용하므로 그 패키지도 작업 트리의 구현을 반영하는지 확인한다.
- 변경 파일의 Pylance 진단과 `CSV.raw()` 반환형을 확인한다. 기존 진단과 신규 진단을 구분하고 기존 Python 3.9 지원 범위를 유지한다.
- 샘플을 기존 파일에서 갱신하면 불필요하게 샘플 수나 샘플 테스트의 개수 계약을 바꾸지 않는다.
- 영향이 관련 테스트 밖으로 확인되면 필요한 범위로 검증을 확대한다. 기존 CI의 설치 패키지 전체 테스트 절차는 유지하며 이 기능 때문에 새 도구·의존성을 추가하지 않는다.
- 문서의 상대 링크, 상태 설명, 코드 예시, 한국어·영어 내용과 `git diff --check`를 확인한다.

## 문서와 기록 반영

- [한국어 상세 매뉴얼](../../../docs/README.md)과 [영어 상세 매뉴얼](../../../docs/README.en.md)에 원문 조회·상태 전이·오류 값과의 차이·컨텍스트 안 예외 처리를 함께 반영한다. 기존 흐름도에 원문 보존 시점을 표시할 필요도 검토한다.
- [거부 기록 샘플](../../../samples/reject_records.py)을 활용해 실패 원문 조회·저장 방법을 보여 준다. 같은 설정의 writer를 사용하는 CSV 덤프 예시를 매뉴얼에 제공하고 실행 결과를 검증한다.
- 루트 한국어·영어 README의 요약과 안내를 검토하고 공개 API 소개에 필요한 부분만 함께 갱신한다. 상세 계약은 매뉴얼에 둔다.
- 의미 있는 구현 단계는 `implements/`에, 테스트·조사·예시 검증은 `tasks/`에 수행하면서 기록한다. 각 디렉터리와 종합 문서는 해당 작업이 실제 발생할 때만 만든다.
- 구현 결과는 `IMPLEMENTS.md`, 구현 외 결과는 `TASKS.md`에 종합하고 이슈 README와 이 계획의 상태를 갱신한다.
- 사용자 매뉴얼 반영 후 실제 제공한 동작만 `CHANGELOG.md`에 작성한다. 현재 계획 작성만으로 기능이 제공된 것처럼 변경 로그를 만들지 않는다.

## 호환성·완료 기준

저장 데이터나 설정의 마이그레이션은 없다. 기존 오류·Pattern 시그니처와 읽기 동작을 그대로 두는 API 추가이므로 별도 전환·복구 절차는 필요하지 않다. 자동 저장·재삽입, 원문 이력, 새 dialect 옵션, 자동 오류 복구는 구현하지 않는다.

인수 기준별 실제 결과, 문서와 구현의 일치, 무관한 변경·개인 경로·임시 파일 혼입 여부를 확인한 뒤에만 구현 완료로 표시한다. 미실행 검증이나 제한사항은 기록하며, 커밋·푸시·PR 생성·병합·이슈 종료는 별도 요청 없이 수행하지 않는다.
