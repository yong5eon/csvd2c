# 검증 실패 원본 맥락 전달 요구사항

## 목적과 근거

[이슈 원문과 작업 메타데이터](./README.md)를 기준으로, 행·열 검증 실패 시 해당 Pattern에 들어온 값과 실패 위치를 행·열 Error 예외로 받을 수 있도록 한다.

후속 사용자 요청에 따라 별도 `handle()` 진입점 대신 Pattern·Validator의 `__call__` 계약 변경으로 위치를 전달한다. Error는 예외 클래스이며 행 Error는 메시지·라인 번호·행 값, 열 Error는 메시지·라인 번호·열 식별자·열 값을 담는다. 이 명세의 원본값은 해당 Pattern의 입력값이며 파일 최초 값이나 검증 체인 시작 값이 아니다. 원본 이슈의 최초 원본 보존 요구는 이 후속 확인으로 대체한다.

## 현재 구조 분석

- [행 Error](../../../src/row/Error.py)는 실패 시점의 `List[str]`, [열 Error](../../../src/column/Error.py)는 실패 시점의 `str`만 받는다. 실패 원인·라인·원본 맥락은 전달하지 않는다.
- [행 Validator](../../../src/row/Validator.py)와 [열 Validator](../../../src/column/Validator.py)는 Pattern 반환값을 순차 전달한다. 앞선 Pattern이 값을 변경하면 다음 Pattern이 변경된 값을 받는 것이 의도한 동작이다.
- [CSV의 검증 흐름](../../../src/CSV.py)은 행 검증 후 열 검증을 실행한다. 행 Pattern은 필드 순서·개수를 바꿀 수 있으므로 열 검증 인덱스와 원본 필드 인덱스의 동일성을 가정할 수 없다.
- 현재 명시적인 데이터 실패 분기가 있는 기본 행 Pattern 9개와 열 Pattern 14개는 이미 Error를 지원한다. Error 연결의 일괄 신설보다 기존 실패 분기의 입력값과 위치 전달이 핵심이다.
- [IfLength](../../../src/row/patterns/IfLength.py)는 중첩 실행의 `ValueError`를 잡아 외부 Error에 전달한다. 내부 Error 구현이 발생시킨 `ValueError`까지 복구 값으로 바꾸는 동작은 예외 전파 요구에 맞게 보완해야 한다.

## 포함 범위

### R1. 기존 Error의 호출 계약 변경

- 행 실패는 기존 `csvd2c.row.Error`, 열 실패는 기존 `csvd2c.column.Error`로 처리한다.
- `src/Error.py`에 최상위 공통 `Error` 클래스를 추가한다. `src/row/Error.py`의 행 Error와 `src/column/Error.py`의 열 Error는 모두 이 공통 Error를 상속한다.
- 실패 위치를 식별할 수 없는 경우 행·열 정보를 만들어내지 않고 공통 Error를 이용한다.
- 특정 컬럼이 없는 행 단위 실패는 행 Error의 대상이다. 헤더가 없어도 숫자 인덱스로 열을 식별할 수 있으면 열 Error를 이용한다. 단순히 컬럼명이 없다는 이유로 공통 Error로 처리하지 않는다.
- 라이브러리의 검증 Pattern은 데이터 실패 시 입력값과 위치를 담은 행·열 Error 예외를 발생시킨다. 사용자 정의 Pattern에 예외 발생을 강제하지 않으며, 예외 발생 여부·예외 타입은 사용하는 쪽에서 결정한다.
- 사용자 지시에 따라 Error는 예외 클래스이다. 공통 Error는 `Exception`을 상속하고 `message`를 받는다. 행 Error는 `__init__(message, row, value: List[str])`, 열 Error는 `__init__(message, row, column: Union[int, str], value: str)`이며 같은 이름의 속성으로 정보를 제공한다. Error는 `__call__`을 갖지 않으며 처리기(handler)가 아니다.
- Pattern의 `error=` 매개변수와 호출형 Error 처리기는 제거한다. 기록·복구·건너뛰기는 호출자가 `try`/`except`로 처리한다.
- Pattern·Validator의 `__call__` 계약을 변경하여 위치를 직접 전달한다. 별도의 `handle()` 실행 계층을 요구하지 않는다.
- 행 Pattern·Validator의 호출 계약은 `__call__(self, value: List[str], row: int) -> List[str]`이다.
- 열 Pattern·Validator의 호출 계약은 `__call__(self, value: str, row: int, column: Union[int, str]) -> str`이다. 열 식별자는 `Optional`이 아니다.

| 정보 | 행 Error 속성 | 열 Error 속성 |
| --- | --- | --- |
| 실패 메시지 | `message` | `message` |
| 실패한 Pattern의 입력값 | `value: List[str]` | `value: str` |
| 실패 레코드의 라인 번호 | `row` | `row` |
| 열 식별자 `Union[int, str]` | 없음 | `column` |

- 실패 이유는 각 Pattern이 `message`로 정한다. 별도의 최초 원본 값은 포함하지 않는다.
- 열 식별자는 인덱스와 컬럼명을 별도 필수 인자로 나누지 않고 `Union[int, str]`로 전달한다. 숫자는 0부터 시작하는 검증 대상 인덱스, 문자열은 컬럼명을 의미한다. 튜플로 지정한 열 Validator는 숫자 인덱스, 이름으로 지정한 열 Validator는 지정한 컬럼명을 전달한다.
- 열을 식별할 수 없으면 열 Error에 `None`을 넣는 대신 공통 Error를 사용한다. 직접 호출자는 행 호출에 라인 번호, 열 호출에 라인 번호와 열 식별자를 제공한다.
- 이 타입은 열의 식별 정보에 적용한다. 처리 중 컬럼 값의 `str` 계약은 변경하지 않는다.
- 데이터 검증 실패는 더 이상 `ValueError`가 아니다. 생성자 설정 오류는 기존처럼 `TypeError`·`ValueError`를 즉시 발생시킨다.

### R2. 라인 번호의 의미

- CSV에서 라인 번호는 파일의 첫 물리 라인을 1로 세는 정수이며, 실패 레코드를 읽은 직후의 마지막 물리 라인 번호 하나를 전달한다.
- 인용 개행이 없는 레코드는 해당 레코드의 라인 번호를 전달한다. 인용 개행이 있는 레코드는 마지막 물리 라인을 전달한다.
- 예를 들어 헤더가 1번 라인이고 다음 레코드가 2~3번 라인에 걸치면, 해당 레코드의 검증 실패 라인 번호는 3이다.
- 이 번호를 오류 문자가 있는 정확한 라인이나 논리 레코드 번호로 표시하지 않는다. 시작·끝 범위나 별도 논리 레코드 번호는 추가하지 않는다.
- 직접 호출 시에도 라인 번호는 `int`이다. 위치를 식별할 수 없는 실패는 공통 Error의 대상으로 구분하며, 행·열 호출을 위해 임의의 번호를 생성하거나 `None`을 전달하지 않는다.

### R3. Pattern 입력값과 위치 전달

- CSV는 레코드를 읽은 직후 라인 번호를 확보하고 Validator에 전달한다.
- 각 Validator는 앞선 Pattern의 반환값을 다음 Pattern의 입력값으로 전달한다. 실패한 Pattern은 자신에게 들어온 값을 담아 Error를 발생시킨다.
- 예를 들어 `Strip`이 `"   "`을 `""`로 바꾼 후 `Required`가 실패하면 Error가 받는 값은 `""`이다. `"   "`을 별도로 보존하거나 전달하지 않는다.
- 중첩 Validator·Pattern도 그 시점에 들어온 값을 처리하며 동일한 라인 번호와 열 식별자를 이어서 전달한다.
- 파일 최초 값·검증 체인 시작 값의 스냅샷, 전체 원본 행의 열 Error 전달, 변환 전 필드 역추적은 요구하지 않는다.
- 입력 헤더가 없으면 숫자 인덱스로 열을 식별하며 컬럼명을 만들어내지 않는다. `header()`가 읽은 입력 헤더와 `row(header=...)`·`rows(header=...)`의 출력용 헤더를 혼용하지 않는다.
- 열 검증은 행 Pattern 처리가 완료된 행을 기준으로 수행한다. 재정렬·병합·분할·삽입·삭제 후에도 열 인덱스는 변경된 행의 위치를 의미한다.
- 이름 지정 열 Validator의 기존 헤더 기반 인덱스 선택 계약은 유지하며, 선택된 위치의 변경된 열에 적용한다.

### R4. Pattern별 적용 범위

| 분류 | 대상 | 필요한 변경 |
| --- | --- | --- |
| 행 검증·실패 가능한 변환 | `Length`, `RejectEmpty`, `RejectHeader`, `Remove`, `Replace`, `Split`, `Merge`, `Reorder` | 기존 실패 분기에서 입력 행·라인 번호를 담은 행 Error 발생 |
| 행 조건부 실행 | `IfLength` | 중첩 입력값·라인 전달, 내부 예외의 재처리 없이 전파 |
| 열 검증·실패 가능한 변환 | `Required`, `Length`, `Choices`, `Regex`, `Map`, `Number`, `Range`, `Date`, `Currency`, `RejectCharacters`, `RejectReplacementCharacter`, `RejectSurrogates`, `Recode`, `RecoverEncoding` | 기존 실패 분기에서 입력값·라인 번호·열 식별자를 담은 열 Error 발생 |
| 열 조건부 실행 | `IfEmpty`, `IfMatch`, `IfUndecodable` | 중첩 Validator에 맥락 전달, 기존 조건과 예외 전파 유지 |
| 사용자 정의 Pattern | 사용자 정의 행·열 검증 Pattern | 변경된 `__call__`과 Error 호출 계약을 적용할 수 있는 예시 제공 |

- `Range`의 숫자 형식 실패와 범위 실패, `Date`의 유효 날짜 없음과 복수 해석 등 기존에 다른 실패 사유는 처리 정책에서 구분한다. 실패 원인을 별도 호출 인자로 추가하지 않는다.
- Error 호출에서 발생한 예외를 같은 검증 실패 분기가 다시 잡아 처리하지 않는다.
- 생성자의 잘못된 설정은 기존처럼 즉시 예외를 발생시킨다. 이를 행·열 Error로 바꾸지 않는다.
- 순수 변환 Pattern에 새로운 거부 조건이나 Error 옵션을 일괄 추가하지 않는다. 호출 계약 변경에 필요한 수정은 적용한다.
- `TryRecoverEncoding`의 후보 복구 실패 시 입력을 그대로 반환하는 명시된 계약은 유지한다.

### R5. 기존 동작과 호환성

- 기존 사용자 정의 Error·Pattern 및 Validator 직접 호출은 변경된 `__call__` 계약에 맞게 수정해야 할 수 있다. 기존 한 인자 구현과의 무변경 호환을 보장하지 않는다.
- 변경된 시그니처, 직접 호출 방법, 기존 구현의 수정 방법을 관련 사용 문서와 예시에 명시한다. 호환성을 위해 호출 예외를 잡아 구형 계약으로 재호출하지 않는다.
- 정상 입력 반환값, 행 검증 후 열 검증의 순서, Pattern 적용 순서를 유지한다.
- 사용자 정의 Pattern에 예외 발생을 강제하지 않는다. 기록·복구·건너뛰기 정책은 사용하는 쪽의 책임이며, 라이브러리는 위치를 담은 예외와 그 전파 계약을 제공한다.
- 중첩 Pattern이 발생시킨 예외를 그대로 전파한다. 중첩 조건 Pattern이 이를 잡아 다른 값으로 바꾸어서는 안 된다.
- 검증 실패는 이미 파싱된 레코드를 소비한 뒤 발생한다. 호출자가 예외를 처리한 뒤 다음 `CSV.row()`를 호출하여 다음 레코드를 읽을 수 있어야 한다.
- 예외로 종료된 동일한 `rows()` Generator의 재개를 새로 보장하거나 자동 건너뛰기를 추가하지 않는다.
- CSV 파싱·파일 디코딩 실패는 Pattern 검증 실패와 구분한다. 확보하지 못한 원본이나 위치를 추측하여 Error 맥락을 만들지 않는다.
- CSV에 Validator를 직접 주입하는 기존 사용 방식을 유지한다. 호출자가 원본 맥락 확보를 위해 검증 루프를 재구현할 필요가 없어야 한다.

### R6. 문서와 예시

- 관련 한국어·영어 사용 문서에 변경된 호출 계약, 라인 번호 의미, 원본의 범위와 호환성 영향을 반영한다.
- 공통 Error와 행·열 Error의 상속 관계, 식별 불가능한 실패의 처리 방법과 확보하지 못한 정보의 표현을 설명한다.
- 사용자 정의 행·열 Pattern이 행·열 Error를 발생시키는 예시와, 호출자가 예외를 잡아 속성을 기록하고 다음 레코드를 읽는 예시를 제공한다.
- 예시의 공개 API·호출 방법은 실제 구현과 일치해야 하며 비민감 합성 CSV를 사용한다.

## 제외 범위

- 파일 경로·출력 형식·재처리 CLI의 제품 기능 추가
- 외부 프로젝트의 사용자 정의 Pattern 직접 수정
- 정확한 파일 원문·원본 바이트 복원, 파싱·디코딩 실패의 원본 재구성
- 파일 최초 값·검증 체인 시작 값의 별도 보존 및 변환 전 필드 역추적
- 시작·끝 물리 라인 범위와 별도의 논리 레코드 번호
- 순수 변환 Pattern의 검증 기능 일괄 확장
- 검증 실패 자동 건너뛰기, 재시도, 동시성 제어 및 별도 오류 실행 계층

## 인수 기준

검증에는 비민감 합성 데이터를 사용한다. 다음 항목은 구현 후 검증할 기준이며, 현재 통과를 의미하지 않는다.

| 기준 | 검증할 결과 |
| --- | --- |
| A1 · R1 | 행 Pattern·Validator는 `(List[str], int) -> List[str]`, 열 Pattern·Validator는 `(str, int, Union[int, str]) -> str` 계약을 사용하고, 행 Error는 `(message, row, value)`, 열 Error는 `(message, row, column, value)` 생성자를 가진 예외 |
| A1-1 · R1 | 튜플 지정은 `int` 인덱스, 이름 지정은 `str` 컬럼명을 열 식별자로 전달하며 컬럼 값은 `str` 유지 |
| A1-2 · R1 | `src/Error.py`에 공통 Error가 정의되고 행·열 Error가 모두 이를 상속하며 식별 불가능한 검증 실패는 공통 Error로 처리 |
| A1-3 · R1 | 특정 컬럼이 없는 행 실패는 행 Error, 헤더 없이 인덱스로 식별 가능한 열 실패는 열 Error로 처리하며 공통 Error가 발생시킨 예외도 그대로 전파 |
| A2 · R2 | 일반 CSV의 라인 번호, 헤더 소비 이후 번호, 인용 개행 레코드의 마지막 물리 라인 번호가 정확히 일치 |
| A3 · R3 | `Strip("   ")` 후 `Required` 실패에서 Error가 `""`를 수신하며, 앞선 행 변환 후에도 실패한 Pattern의 입력 행을 수신 |
| A4 · R3 | 중첩 Validator·Pattern이 그 시점의 입력값과 동일한 라인 번호·열 식별자를 전달 |
| A5 · R1·R3 | 헤더 없는 입력은 숫자 열 식별자를 사용하고 직접 호출은 명시적 위치를 제공하며, 식별 불가능한 실패는 공통 Error로 처리 |
| A6 · R3 | 행 재정렬·병합·분할·삽입·삭제 후 변경된 행 기준으로 열을 검증하고 변환 전 값 보존·역추적을 수행하지 않음 |
| A7 · R1·R4 | 라이브러리 검증 Pattern이 해당 입력값과 위치를 담은 행·열 Error를 발생시키며 사용자 정의 Pattern에 일괄적인 예외 발생을 강제하지 않음 |
| A8 · R4·R5 | 생성자 설정 오류와 `TryRecoverEncoding`의 명시된 후보 실패 동작 유지 |
| A9 · R1·R5 | Pattern의 `error=` 인자가 없고 데이터 실패는 `ValueError`가 아닌 행·열 Error이며, 정상 입력 반환값·검증 순서를 유지 |
| A10 · R5 | 중첩 Pattern의 예외가 중첩 `IfLength`를 포함하여 그대로 전파 |
| A11 · R5 | 인용 개행 레코드의 검증 실패 후 다음 `CSV.row()`로 다음 레코드 읽기 가능 |
| A12 · R5 | 파싱·파일 디코딩 실패를 검증 Error로 변환하지 않고 원본·위치를 추측하지 않음 |
| A13 · R6 | 사용자 정의 행·열 Error·Pattern 예시와 CSV 직접 주입 예시가 변경된 API로 실행되며 마이그레이션 설명과 일치 |

## 현재 상태

요구사항 명세와 [작업 계획](./PLAN.md)에 따라 구현과 검증을 완료했다. 초기 구현의 호출형 Error 처리기 설계는 사용자 지시에 따라 예외 클래스 설계로 정정했다. 구현 결과는 [구현 종합 기록](./IMPLEMENTS.md), 분석과 검증 결과는 [작업 종합 기록](./TASKS.md)에 정리한다.
