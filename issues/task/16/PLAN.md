### 후속 작업 8의 변경·검증 계획

1. `INSTRUCTIONS.instructions.md`에서 단순 의견과 자료 확인이 필요한 검수를 구분하고, 검수만으로 파일 수정·외부 변경이 허용되지 않음을 명시한다.
2. `AGENTS.md`의 코드 작업 안내에서 상세 매뉴얼과 루트 README 지침으로 연결하고, 영향 확인·필요한 갱신·불필요한 이유 기록을 안내한다.
3. `TASK.instructions.md`의 주요 작업 계획 항목을 실제 작업에 해당하는 대상·역할로 표현해 비코드 작업에 코드 구성요소를 강제하지 않는다.
4. 기존 기록을 보존하고 사용자의 한·영 지침 원복과 에이전트의 잘못된 설명을 후속 근거·작업 기록에 정정한다.
5. 각 지침의 적용 범위와 필수 규칙, 변경한 문서의 상대 링크를 확인한다. 문서만 변경하므로 제품 테스트는 실행하지 않는다.

PR 본문 경로를 CI가 읽도록 구현하고 로컬에서 검증했다. 실제 GitHub Actions와 에이전트 세션 검증은 수행하지 않았다.

### 후속 작업 9의 변경·검증 계획

1. `.github/scripts/create-pr-from-issue.mjs`의 `createPullRequest`가 새 PR 생성 전에 읽은 변경 로그의 누락·공백 여부를 검사해 실패를 명시한다. 이미 열린 PR의 처리 분기는 변경하지 않는다.
2. `buildPullRequest`의 모든 본문 생성 경로에서 `Closes`와 `Changes:`를 마지막 두 목록 항목으로 작성한다. 기존 길이 제한 계산에 이 항목을 포함한다.
3. `.github/scripts/tests/create-pr-from-issue.test.mjs`에서 정상·누락·빈 변경 로그, 기존 PR 본문 보존, 본문 크기 경계와 링크 대체 경로를 검증한다.
4. 상세 매뉴얼과 루트 README의 영향 여부를 판단하고 실제 결과를 이슈 기록과 변경 로그에 남긴다. CI 변경과 실제 GitHub PR 생성·수정은 이번 범위가 아니다.

### 후속 작업 10의 변경·검증 계획

5. 사용자용 매뉴얼과 루트 README의 영향 여부를 검토하고 변경 로그와 작업 기록을 갱신한다. 실제 GitHub PR 생성·수정과 배포는 수행하지 않는다.

2. csvd2c 자동화는 `IR.md`의 마지막 두 항목이 해당 이슈와 경로에 일치하는지 검사하고 중복 없이 본문을 사용한다.

### 후속 작업 21의 변경·검증 계획

1. 두 공통 지침의 형식과 현재 `IR.md`에 `관련 이슈 및 변경 로그` 제목을 추가한다.
2. 마지막 두 항목과 순서를 유지한다. 문서만 변경하므로 자동화 테스트는 재실행하지 않는다.

### 후속 작업 22의 변경·검증 계획

1. `buildPullRequest`는 `IR.md`의 마지막 비어 있지 않은 줄만 해당 이슈의 `Changes:` 경로와 비교한다. 이슈 종료 항목의 개수나 위치는 제한하지 않는다.
2. 릴리즈 노트 수집은 마지막 비어 있지 않은 줄만 해석하며 바로 앞의 중복 항목을 검사하지 않는다. 마지막 줄이 없는 기존 PR의 브랜치 기반 경로와 잘못된 마지막 항목의 오류는 유지한다.
3. 공통 지침에 실제 해결한 이슈마다 플랫폼에 맞는 종료 구문을 작성하도록 안내한다. 관련 PR 자동화와 릴리즈 노트 수집 테스트만 실행한다.

### 후속 작업 23의 변경·검증 계획

1. 워크플로의 `push` 브랜치 목록에 `copilot/**`, `codex/**`를 추가한다. 현재 워크플로는 푸시된 커밋의 스크립트를 실행하므로 에이전트 브랜치도 변경된 워크플로를 포함해야 한다.
2. `createPullRequest`는 에이전트 브랜치의 열린 PR을 조회하고, PR이 없으면 명시적으로 건너뛴다. 열린 PR의 head가 푸시 커밋과 다르면 오래된 실행으로 건너뛴다.
3. [GitHub PR 파일 API](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)를 페이지별로 조회해 삭제되지 않은 이슈 `IR.md` 하나를 찾는다. API의 3,000개 제한에 도달하거나 후보가 없거나 여러 개면 오류로 중단한다.
4. 선택한 문서와 변경 로그를 푸시된 작업 트리에서 읽어 기존 `buildPullRequest`로 제목·본문을 생성하고 열린 PR을 갱신한다. 에이전트 PR의 다른 메타데이터는 변경하지 않는다.
5. 모의 GitHub API 테스트로 두 브랜치, 페이지네이션, 누락·중복, 오래된 커밋과 기존 이슈 브랜치 동작을 확인한다. 실제 Actions나 원격 PR은 수정하지 않는다.

### 후속 작업 24의 변경·검증 계획 — 로컬 구현 및 검증 완료

1. CI의 릴리즈 노트 수집에서 공백 1~3칸으로 들여쓴 마지막 `Changes:` 항목을 원래 줄로 검증해 오류 처리한다. 네 칸 이상·탭 들여쓰기의 기존 폴백은 유지한다.
2. `createPullRequest`는 변경 로그를 읽기 전에 링크 자체의 파일 유형을 확인해 일반 파일이 아니면 PR 생성·갱신을 중단한다.
3. 세 프로젝트에 이미 적용한 공통 테스트를 적용하고 관련 Node·Python 테스트와 공통 코드의 동일성을 확인한다. 실제 GitHub Actions 실행과 원격 변경은 하지 않는다.
